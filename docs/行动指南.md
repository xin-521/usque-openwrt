# usque on OpenWrt：把全部流量交给 WARP（MASQUE）行动指南

> 目标项目：[Diniboy1123/usque](https://github.com/Diniboy1123/usque) —— Cloudflare WARP 客户端的开源 MASQUE/Connect-IP 重实现。
> 本指南基于 **v4.2.1（commit `6aa03fc`，2026-07-20 发布）**、目标系统 **OpenWrt 24.10 / 25.12**。
> 文中每个结论都对应一次实测或源码核对，出处见文末《事实核查与验证记录》。

---

## 0. 先读这一段（结论、能力边界、预期）

**能不能做**：能。usque 的 `nativetun` 模式在 OpenWrt 上会创建一个真实网络接口（本指南用 `warp0`），
把默认路由指过去，路由器自身和所有 LAN 客户端的流量就都走 WARP 了。全流程约 20–40 分钟。

**它适合什么**

- 想让全屋设备（手机/电视/PC）无感走 WARP，不想每台设备装客户端；
- 本地网络对 WireGuard/VPN 有干扰、但对 HTTP/3（QUIC）宽容；
- 需要对 DPI 伪装（改 SNI）、或在 UDP 443 被封时回退到 TCP（`--http2`）。

**它不适合什么（务必先接受这几点）**

- **不是"翻墙"工具**：它连的是 Cloudflare 的 WARP 网络。若你的运营商直接封锁 Cloudflare 网段，
  usque 同样连不上；它也不能帮你把 IP 变成某个特定国家。
- **免费 WARP 是尽力而为**：不保证速度和稳定性，官方随时可能调整策略（本项目是逆向研究性质，非官方支持）。
- **用户态实现**：MASQUE 走 quic-go（用户态 QUIC），吞吐受路由器 CPU 限制。x86 软路由可跑满千兆，
  MT7621 这类老 MIPS 路由器通常只有几十 Mbps。
- **MIPS32 老路由器有硬坑**：官方二进制是 hardfloat 编译的，无 FPU 的 24Kc/74Kc 会 `SIGILL`；
  本指南附带了 softfloat 构建（见步骤 1）。
- **遵守当地法律**：是否可用、可用于什么，请自行判断并承担后果。

**最低要求**

| 项目 | 要求 | 说明 |
|---|---|---|
| OpenWrt | 21.02+（推荐 24.10.x / 25.12.x） | 25.12 起包管理器换成 `apk`，指南两者都覆盖 |
| 内核模块 | `kmod-tun` | `nativetun` 必需，装前要能联网 |
| 工具 | `ip`（busybox 内置即可） | 钩子脚本用 `ip route`；有 `ip-full` 更稳 |
| 存储 | 根分区 ≥ 20 MB 可用 | 二进制约 12–14 MB（已 strip） |
| 内存 | ≥ 128 MB 建议，256 MB 更稳 | Go + 用户态协议栈，实测占用见第 11 节 |
| 出网 | 能访问 `api.cloudflareclient.com`（仅注册用）与 WARP 端点 | 注册建议在 PC 上做 |

## 1. 目标架构

```
        ┌──────────── LAN 客户端（手机/PC/电视，无需任何配置）
        │
   ┌────┴────────────────────────────────────────────────────────────┐
   │ OpenWrt 路由器                                                  │
   │                                                                 │
   │  路由决策： 默认路由 metric 10  →  warp0   ← 隧道可用时全走这里    │
   │             默认路由 metric 250 →  wan     ← 隧道消失时自动兜底   │
   │                                                                 │
   │  usque (nativetun)  ──  /etc/usque/up.sh  (连接后接管路由)        │
   │         │             /etc/usque/down.sh (断线，保持 fail-closed) │
   │         │                                                       │
   │         └── 例外路由  <WARP端点>/32 → wan 网关（保证隧道自己不断） │
   └─────────┬───────────────────────────────────────────────────────┘
             │  QUIC/HTTP3 (UDP 443) 或 HTTP/2 (TCP 443，--http2)
             ▼
      162.159.198.1:443  ──►  Cloudflare WARP 网络  ──►  互联网
```

**怎么确认 CPU 到底有没有 FPU**（MIPS 路由器）：

```sh
grep -m1 -E "cpu model" /proc/cpuinfo      # 看到 24Kc / 74Kc / 34Kc（结尾没有 f）→ 无 FPU
```

### 4.2 传输 + 校验（重要）

```sh
# PC 上（Windows 用 Git Bash / WSL；确保是二进制模式传输）
sha256sum -c dist/SHA256SUMS-bin.txt                # 先核对本地文件
scp dist/bin/usque-linux-mipsle-softfloat root@192.168.1.1:/tmp/usque
```

```sh
# 路由器上

cp /tmp/usque /usr/bin/usque && chmod 755 /usr/bin/usque
/usr/bin/usque version                               # 应打印版本；SIGILL 说明选错浮点版本
```


## 7. 步骤 4：先手动验证隧道（暂不接管路由）

```sh
usque -c /etc/usque/config.json nativetun --interface-name warp0
```

期望日志：

```
Created TUN device: warp0
Tunnel established, you may now set up routing and DNS
Connected to MASQUE server
```

另开一个 ssh 窗口：

```sh
ip -4 addr show warp0                 # 应有 172.16.x.x/32（config 里的 ipv4）
ip link show warp0                    # MTU 1280
ping -c 3 -I warp0 1.1.1.1            # 走隧道能通 → 说明 MASQUE OK
curl --interface warp0 -s https://www.cloudflare.com/cdn-cgi/trace | grep -E '^(ip|warp)='
#   期望： warp=on（或 warp=plus），ip= 是 Cloudflare 出口 IP，不是你 ISP 的 IP
```

> 注意：`curl --interface` 要写**接口名**（warp0），不是 IP；Windows 上的 `curl --interface` 行为不同，别混淆。
> 此时**默认路由还没改**，所以这台路由器其它流量仍走直连——这正是我们想要的"先验证、后接管"。

排障：如果 `ping -I warp0` 不通但日志显示已连接 → 通常是 QUIC/UDP 443 被干扰，先跳到第 10 节试 `--http2`。

## 8. 步骤 5：接管全部流量（核心）

### 8.1 机制：两个钩子 + 两条默认路由

`nativetun` **不会**帮你配路由，所以我们在 usque 每次连接成功后执行 `/etc/usque/up.sh`：

1. **给 WARP 端点加一条走物理 WAN 的例外路由**（`162.159.198.1/32` → WAN 网关）。
   没有它，隧道自己的 QUIC 包会被"默认路由指向隧道"这个动作送进隧道，形成黑洞死循环。
2. **把默认路由指向 `warp0`，metric 10**，同时让 WAN 的默认路由退到 **metric 250**。
   于是：只要隧道接口存在，所有流量（路由器本身 + LAN 客户端）都走 WARP。

掉线时 `/etc/usque/down.sh` **故意不清理路由** —— warp0 还在、隧道路由还在，包会被丢弃（**fail-closed**，
宁可断网也不把明文送到 ISP）；usque 默认每 1 秒重连，重连成功会再次触发 `up.sh`。

**usque 进程彻底退出时**，warp0 设备消失，内核自动删除挂在它上面的默认路由，WAN 的 metric 250 兜底路由立即生效
→ 自动恢复直连，**不会把路由器锁死**。

### 8.2 路由优先级（怎么算都不会错）

| 路由 | metric | 何时生效 |
|---|---|---|
| `default dev warp0`（up.sh 添加） | **10** | 隧道接口存在时永远优先 |
| `default via <WAN网关> dev <WAN>` | 250（需配置） | 隧道接口消失后的兜底 |
| IPv6 `default`（由 RA/DHCPv6 添加） | 通常 1024 | 同上；隧道 v6 路由 metric 10 优先 |

`up.sh` 里带了**自检**：连接后它会用 `ip route get 1.1.1.1` 检查实际出口，若没走 warp0 会写进 `logread` 并给出修法。

```sh
# 如果 WAN 默认路由的 metric 仍是 0（自制固件/多拨环境常见），手工改：
uci set network.wan.metric='250'
uci commit network && /etc/init.d/network reload
ip route show default                 # 确认：default dev warp0 metric 10 在最上面
```

### 8.3 LAN 客户端（防火墙 zone + NAT）

```sh
# 新建 warp zone，并把 LAN→warp 的转发打开（脚本已做，这里给出等价命令）
uci set firewall.warp=zone
uci set firewall.warp.name=warp
uci set firewall.warp.input='REJECT'
uci set firewall.warp.output='ACCEPT'
uci set firewall.warp.forward='REJECT'
uci set firewall.warp.masq='1'        # IPv4 NAT
uci set firewall.warp.masq6='1'       # IPv6 NAT（隧道内是 /128，必须 NAT）
uci set firewall.warp.mtu_fix='1'
uci set firewall.warp.network='warp'  # 对应 network.warp（proto none, device warp0）
uci add_list firewall.warp.device='warp0'   # fw4（22.03+）推荐再加这一条
uci set firewall.lan_warp=forwarding
uci set firewall.lan_warp.src='lan'
uci set firewall.lan_warp.dest='warp'
uci commit firewall && /etc/init.d/firewall reload
```

> 只让路由器自己走 WARP、不想影响 LAN：跳过这一节（不做 LAN→warp 转发）即可。

### 8.4 DNS：别让解析泄漏到 ISP

`nativetun` 模式下 usque **不碰 DNS**（源码确认），所以由 OpenWrt 的 dnsmasq 决定上游。把上游改成 `1.1.1.1`，
它就会跟着默认路由一起走隧道：

```sh
uci set network.wan.peerdns='0'                  # 不再接受运营商下发的 DNS
uci -q delete network.wan.dns
uci add_list network.wan.dns='1.1.1.1'
uci commit network
uci set dhcp.warp_dns=dnsmasq                    # 显式声明上游，防止被其它 dnsmasq 段覆盖
uci -q delete dhcp.warp_dns.server
uci add_list dhcp.warp_dns.server='1.1.1.1'
uci commit dhcp && /etc/init.d/network reload && /etc/init.d/dnsmasq restart
```

验证（路由器上）：

```sh
nslookup one.one.one.one 127.0.0.1                    # 能解析
# 看解析请求最终从哪个 IP 出去（应显示 Cloudflare 侧地址，而不是你 ISP 的）
nslookup -type=txt whoami.ds.akahelp.net 127.0.0.1
```

> 也可以改用加密 DNS（`https-dns-proxy` / `smartdns`），但那属于另一层优化；上面的做法已经保证 DNS 走隧道。

### 8.5 IPv6：三种处理方式（选一种）

1. **WAN 没有 IPv6**（很多国内家宽）→ 什么都不用做，LAN 也就没有 v6，天然无泄漏。
2. **让 IPv6 也走 WARP**（推荐给双栈用户）：`up.sh` 已经加了 `ip -6 route replace default dev warp0 metric 10`，
   再加 `masq6=1`（上面已有）。这时 LAN 客户端的 v6 也经隧道出去。
3. **不想折腾 v6**：在 LAN 关掉 v6 下发，避免"v4 走隧道、v6 直连"的分裂：
   ```sh
   uci set dhcp.lan.dhcpv6='disabled'
   uci set dhcp.lan.ra='disabled'
   uci set dhcp.lan.ra_slaac='0'
   uci commit dhcp && /etc/init.d/odhcpd restart
   ```
   （若你的 LAN 还有 v6 直连需求，别用这个方案。）

### 8.6 策略选择：后备 vs 严格

| | 后备模式（脚本默认） | 严格模式（`--strict`） |
|---|---|---|
| 做法 | WAN 保留 `metric 250` 的默认路由 | `network.wan.defaultroute='0'`，WAN 不产生默认路由 |
| 隧道活着 | 全流量走 WARP | 全流量走 WARP |
| 隧道掉线 | 包被丢弃（fail-closed），重连即恢复 | 同左 |
| usque 进程死掉 | 自动回退直连（**有短暂直连泄漏窗口**） | **完全断网**，直到你修好 |
| 风险 | 极低 | 配置/账号一出错就整网失联；远端管理尤其危险 |

**建议**：除非你有明确"绝不直连"的合规要求，先用默认的后备模式跑几天，确认稳定后再考虑 `--strict`。
真要严格模式，务必先准备好救援手段（见第 12 节）。

## 9. 步骤 6：常驻与开机自启（procd）

`install-on-router.sh` 已装好 `/etc/init.d/usque`。启用：

```sh
/etc/init.d/usque enable
/etc/init.d/usque start
logread -e usque            # 看 usque 与钩子日志（含 up.sh 的出口自检）
```

服务脚本要点（`usque/root/etc/init.d/usque`，发布包内为 `deploy/usque.init`）：

```sh
procd_set_param command /usr/bin/usque -c /etc/usque/config.json nativetun \
    --interface-name warp0 --on-connect /etc/usque/up.sh --on-disconnect /etc/usque/down.sh \
    $USQUE_EXTRA_ARGS
procd_set_param respawn 3600 5 10     # 崩溃自动拉起（1 小时内最多 10 次）
procd_set_param stdout 1              # 日志进 syslog
procd_set_param stderr 1
procd_set_param file /etc/usque/config.json   # 配置改了自动重启
```

- `--always-reconnect`（默认开启）：空闲也保持重连，适合"常在线"的路由器；
  去掉它则"只有新流量才触发重连"（更省流量，但掉线期间更久才恢复）。
- 参数集中在 `/etc/usque/options.sh`，改完 `/etc/init.d/usque restart` 生效。
- 想改 MTU/SNI/端口/http2，都在 `USQUE_EXTRA_ARGS` 里（见下一节）。

**可选：双重看门狗**（procd respawn 之外再加一层，防止"进程活着但隧道长期不通"）：

```sh
# 每 5 分钟检查一次，隧道不通就重启 usque（先手动确认这个逻辑适合你）
cat >> /etc/crontabs/root <<'EOF'
*/5 * * * * ip link show warp0 >/dev/null 2>&1 || /etc/init.d/usque restart
EOF
/etc/init.d/cron enable && /etc/init.d/cron restart
```

> 注意：`--persist` 参数**不要用**。它会让 warp0 在 usque 退出后仍存在，于是"隧道消失 → 兜底路由生效"
> 这条安全路径失效，容易造成整网黑洞。

## 10. 步骤 7：抗封锁调优（对应 README 的 *Censorship circumvention*）

README 原文要点：MASQUE 流量与普通 HTTP/3 很难区分，但 QUIC 强制 TLS 1.3，握手会带
`client-masque.cloudflareclient.com` 这个 SNI，**有些防火墙/DPI 就卡这个字符串**；用 `-s` 换成任意域名仍然能连通。

### 10.1 先做一次"分层探测"，确定被卡在哪一层

在路由器上（**保持 usque 停着**，用前台命令逐个试）：

```sh
# ① 基础连通：能不能到 WARP 端点
ping -c2 162.159.198.1
# ② UDP/443 是否被丢：MASQUE 默认走 QUIC(UDP)
usque -c /etc/usque/config.json nativetun --interface-name warp0      # 默认 QUIC
# ③ UDP 被卡 → 换 TCP/HTTP2（端口仍是 443，但走 TCP+TLS）
usque -c /etc/usque/config.json nativetun --interface-name warp0 --http2
# ④ SNI 被卡 → 伪装 SNI（QUIC 模式下同样有效）
usque -c /etc/usque/config.json nativetun --interface-name warp0 -s www.bing.com
# ⑤ 端口被卡（有的网络只放行 443/80）→ 换端口
usque -c /etc/usque/config.json nativetun --interface-name warp0 -P 500
# ⑥ 只有 IPv6 可用 / 想避开 v4 干扰
usque -c /etc/usque/config.json nativetun --interface-name warp0 -6
```

判定：哪一条能出现 `Connected to MASQUE server`，就把对应参数写进 `/etc/usque/options.sh` 的 `USQUE_EXTRA_ARGS`。

### 10.2 参数速查

| 参数 | 作用 | 什么时候用 |
|---|---|---|
| `-s <域名>` | 改写 TLS SNI（默认 `consumer-masque.cloudflareclient.com`） | DPI 按 SNI 拦；选一个大站/CDN 域名更不显眼 |
| `--http2` | 改用 TCP + HTTP/2（端点 `endpoint_h2_v4`，默认 162.159.198.2） | UDP 443 被限速/丢弃、QUIC 被 QoS |
| `-P <端口>` | 换连接端口（443 / 500 / 1701 / 4500 / 53 等） | 网络只放行特定端口 |
| `-6` | 用 IPv6 连 WARP 端点（需 `endpoint_v6` 可达） | 家宽 v4 到 Cloudflare 路由差、v6 更顺 |
| `--keepalive-period 30s` | 缩短保活间隔 | 中间 NAT 空闲踢连接 |
| `-i <大小>` | 自定义 initial packet size | 少见：MTU 异常时配合排障 |
| `--insecure` | 关闭端点公钥 pinning | **仅临时排障**，长期禁用会失去防中间人能力 |
| `--local-dns` / `--system-dns` | 仅 socks/http-proxy 模式 | nativetun 不适用 |

### 10.3 火坑提醒

- **L4 模式（`l4-socks`/`l4-http-proxy`）在封锁环境基本没用**：它只能用 QUIC、**不能改 SNI**，而且目标 UDP 不支持。
  只有在"QUIC 通畅、只要最省资源做 TCP 代理"时才用它。
- `--http2` 下想去 IPv6 端点，必须自己在 config 里填 `endpoint_h2_v6`（默认是空的）：
  ```json
  "endpoint_h2_v6": "2606:4700:103::"
  ```
- 改完 `options.sh` 记得 `restart`，并看 `logread -e usque` 确认连上的是哪种模式。

## 11. 步骤 8：性能与资源（别指望老路由器跑满千兆）

### 11.1 必做：加大 UDP 缓冲（quic-go 官方建议）

```sh
sysctl -p /etc/sysctl.d/90-usque.conf
sysctl net.core.rmem_max net.core.wmem_max     # 期望 7500000
```

### 11.2 MTU：别改

默认 `-m 1280` 且已启用 PMTU 自动发现。源码里明确写了：**非 1280 的 MTU 不受支持**，会掉包。
（若上层是 PPPoE，确保 WAN MTU ≥ 1492 即可，隧道内 1280 足够。）

### 11.3 观测实际消耗

```sh
PID=$(pidof usque)
grep -E "VmRSS|VmHWM|Threads" /proc/$PID/status      # 常驻内存
top -b -n1 | head -12                                # CPU 占用（跑一次测速时观察）
cat /proc/net/dev | grep warp0                       # 隧道收发字节
```

### 11.4 预期吞吐（要事先有数）

| 硬件档位 | 大致预期 | 说明 |
|---|---|---|
| x86/64 软路由 | 数百 Mbps ~ 近千兆 | README 实测 Ryzen 上 SOCKS 模式 833/772 Mbps |
| 现代 ARM（MT7981/A53 等） | 约 50–250 Mbps | 受 CPU 单核与用户态协议栈限制 |
| 老 MIPS（MT7621/24Kc） | 约 5–40 Mbps | 且 **必须用 softfloat**；可能只有十几 Mbps |
| 老 ARMv5/ARMv6 | 几 Mbps ~ 十几 Mbps | 只适合轻量使用 |

优化手段（按收益排序）：

1. 换更好的硬件（x86 或 A53 以上）；
2. 降低 `--keepalive-period` 频率、开启 `--always-reconnect` 的取舍（保持连接比反复握手更划算）；
3. 只让必要设备/网段走 WARP（不用全屋做主路由）；
4. 确属 TCP-only 需求再考虑 L4 模式（但要接受 10.3 的限制）。

### 11.5 免费 WARP 与 WARP+

- 免费版够用来"让流量走 Cloudflare"，但线路不保证；
- `usque account set <license>` 可挂 WARP+ 许可，`usque account info` 查看当前状态；
- ZeroTrust 用户：`usque register --jwt <team-token>`，且 README 建议 SNI 用 `zt-masque.cloudflareclient.com`。

### 11.6 arm64（ARMv8）专版构建与调优

只给 aarch64 路由出一份二进制时：

```sh
sh tools/build_arm64_v8.sh      # 产物 dist/bin/usque-linux-arm64（约 11.6 MiB）
sh tools/make-bundle.sh arm64   # → dist/usque-deploy-arm64.tar.gz
```

- **必须 `GOARM64=v8.0`**：OpenWrt 的 aarch64 覆盖 Cortex-A53/A72（v8.0，无 LSE）到 A76（v8.2，有 LSE）。
  抬到 `v8.1` 会把 LSE 原子指令编进代码，A53/A72 上直接 SIGILL；v8.0 是唯一通吃基线。
- 构建参数已钉死：非 PIE（无重定位开销）、`-trimpath`、`-s -w -buildid=`、`CGO_ENABLED=0`；
  脚本用 `go version -m` + ELF 头自检，架构/基线不对直接失败；SHA256 记在 `dist/MANIFEST.tsv`。
- 运行时调优（可选、可回滚）：

```sh
sysctl -p /etc/sysctl.d/90-usque.conf     # rmem/wmem 7.5MB + netdev_max_backlog
sh deploy/tune-arm64.sh                   # 只看现状
sh deploy/tune-arm64.sh --apply           # governor=performance + packet_steering=1
sh deploy/tune-arm64.sh --revert          # 全部还原
```

- `performance` 会提高待机功耗与温度，无风扇设备先看 `/sys/class/thermal/thermal_zone*/temp`。
- 用户态 QUIC 的硬上限仍是**单核**：跑测速时看 `top -b -n1 | head -12`，
  若单个 usque 线程吃满一核，调参数也无济于事，只能换 CPU 更强的设备。

## 12. 步骤 9：验收清单（逐条打勾）

**在路由器上**

```sh
# 1) 服务在跑、接口在
/etc/init.d/usque status ; ip link show warp0

# 5) 端口/SNI 情况（按需）
netstat -anu | grep 443     # 有到 162.159.198.1:443 的 UDP 连接（QUIC 模式）
```

**在 LAN 客户端上**

```sh
curl -s https://www.cloudflare.com/cdn-cgi/trace | grep -E '^(ip|warp)='

# DNS 是否泄漏（结果应是 Cloudflare 侧地址）
```

```sh
reboot
```

```sh
/etc/init.d/usque stop
```

## 13. 故障排查表

| 现象 | 可能原因 | 处理 |
|---|---|---|
| `Config not loaded. Please register first.` | config.json 不存在/路径不对 | 检查 `-c` 路径与文件内容；重新 `register` |
| 找不到二进制 `…/deploy/dist/bin/usque-linux-*` | 安装脚本在 `deploy/` 子目录里运行（包根才是工作目录） | `cd` 到含 `dist/` 的包根再跑 `sh install-on-router.sh`；旧包里可 `cp deploy/install-on-router.sh .` 后重跑 |
| `Failed to create TUN device` | 没装 `kmod-tun`、非 root、或 `/dev/net/tun` 不存在 | `apk add kmod-tun`；用 root 运行；`ls -l /dev/net/tun` |
| `Illegal instruction` 立即崩溃 | MIPS 官方二进制是 hardfloat，CPU 无 FPU | 换 `usque-linux-mipsle-softfloat` / `mips-softfloat` |
| 日志反复 `H3_NO_ERROR` 断线 | Cloudflare 侧空闲回收（正常行为） | 加 `--always-reconnect`；或调小 `--keepalive-period` |
| 反复 `PROTOCOL_VIOLATION` | QUIC 路径有中间设备干扰 | 升级到 v4.2.1（已针对该错误优化）；仍不行就 `--http2` |
| 能连上但客户端没网 | 路由/防火墙/DNS 没配好 | 按第 12 节 1–4 条逐项检查；确认 `masq=1`；`logread -e usque` 看自检 |
| LAN 能上网但 DNS 很慢/失败 | 上游 DNS 被拦或未被隧道承载 | 检查 `network.wan.peerdns=0`、`dns=1.1.1.1`；`/etc/init.d/dnsmasq restart` |
| LAN 客户端 v6 能直连（泄漏） | 双栈分裂 | 见 8.5：让 v6 也走隧道，或关掉 LAN v6 下发 |
| 隧道建立成功但速度极慢 | quic-go 的 reno 拥塞控制 + 路由器 CPU 弱 | 加大 UDP 缓冲；换硬件；别改 MTU |
| 重启后不工作 | 服务没 enable / kmod-tun 没装 | `/etc/init.d/usque enable`；检查 `/etc/rc.d/S95usque` |
| SSH 突然断开、连不上 | 远端管理时把默认路由改错了（自锁） | 见第 14 节自救 |
| 安装时出现 `!! 命令失败: uci -q delete xxx` | 该 UCI 键本来就不存在，旧版脚本把返回码当错误 | 无害可忽略；新版脚本改为「不存在则跳过」，不再报错 |
| `tls: failed to verify certificate`（注册时） | 缺系统 CA | `apk add ca-bundle` / `opkg install ca-bundle` |
| 注册 `429` | WARP 注册频率限制 | 等几分钟再试；换网络环境（或在 PC 上注册） |
| 时间不对导致握手失败 | 路由器时间未同步 | `uci set system.ntp.enabled=1; /etc/init.d/sysntpd restart` |

## 14. 回滚与自救

### 14.1 一分钟回滚（保留配置）

```sh
/etc/init.d/usque stop        # 立即：warp0 消失 → WAN 兜底路由生效 → 恢复直连
```

### 14.2 完整回滚（连 UCI 改动一起撤销）

```sh
cd /root/usque-deploy && sh install-on-router.sh --rollback
```

回滚会先把手上的注册信息备份到 `/root/usque-config.json.bak`，再删除 `/etc/usque`；
重新安装后把它拷回 `/etc/usque/config.json`（`chmod 600`）即可免二次注册。

### 14.3 自锁救援（远端 SSH 把自己关在外面时）

1. 若还能进 LuCI：删掉 `network.wan.defaultroute='0'`（严格模式的关键项），或直接
   把 `network.warp` 接口删掉 → `/etc/init.d/network reload`。
2. 若完全进不去：
   - **LAN 侧 SSH 仍然有效**（LAN 是同网段直连，不经过默认路由），用网线/局域网连上照上面改；
   - 有物理按键的路由器：进入 **failsafe 模式**（开机瞬间按 reset，OpenWrt 会禁用大部分配置并给出 `192.168.1.1`），
     修好 `/etc/config/network` 再重启；
   - 最后一招：`firstboot`（恢复出厂，会丢配置，务必先备份）。
3. **预防**：开启服务前先加一个"定时自动回滚"看门狗（示例，确认可用后再删掉）：

```sh
# 10 分钟后如果没手动 touch /root/usque-ok，就自动停服务并恢复 WAN 默认路由
( sleep 600; [ -f /root/usque-ok ] || { /etc/init.d/usque stop; uci -q delete network.wan.defaultroute; uci -q delete network.wan.metric; uci commit network; /etc/init.d/network reload; } ) &
```

### 14.4 备份（动手前 30 秒的事）

```sh
tar czf /root/openwrt-backup-$(date +%F).tar.gz /etc/config /etc/usque 2>/dev/null
```

### 15.4 事实核查与验证记录（可复现）

本指南的结论由以下命令/产物支撑（复现命令在括号内）：

1. **官方 release 资产与校验**：15 个资产全量列出 + `checksums.txt` 逐包 SHA256 比对，9 个 Linux 包全部 `OK`
   （`python tools/fetch_release.py --download mipsle mips arm64 armv7 armv6 armv5 amd64 mips64 mips64le`）。
2. **二进制真实性**：`go version -m` 读出 `GOOS/GOARCH/GOARM/GOMIPS` 与 `vcs.revision=6aa03fc…`，
   且 15 个包内均含 `4.2.1` 版本戳（`python tools/check_binaries.py`）。
3. **MIPS 浮点结论**：官方 `mipsle` 的 `.text` 反汇编出 **3922** 条 COP1/浮点指令（`.MIPS.abiflags` 为 `ANY`，但
   `go version -m` 显示 `GOMIPS=hardfloat`）；自建 softfloat 版本为 **0** 条（`python tools/scan_fpu.py …`）。
4. **路由钩子逻辑**：mock `ip`/`logger` 回归 5 个场景（v4 端点、v6 端点、`replace` 失败回退、无物理默认路由时安全退出、
   WAN metric=0 告警），输出命令序列符合预期（`sh tools/test_up_hook.sh`）。
5. **脚本可移植性**：全部脚本已统一为 LF 行尾并通过 `sh -n` 语法检查（CRLF 会导致 OpenWrt 上 `bad interpreter`）。
6. **OpenWrt 事实**：25.12.6 包索引为 `packages.adb`（apk）、24.10.5 为 `Packages.gz`（opkg）；
   架构名经逐个 HEAD 探测确认；官方包索引中无 usque（4528 个包全文检索）。

**尚未验证（需要在你的设备上完成）**：`install-on-router.sh` 对真实 UCI/fw4 的改动、真实路由器上的
吞吐与内存占用、MIPS softfloat 二进制在你具体 CPU 上的表现。装完请按第 12 节验收清单逐项确认。
